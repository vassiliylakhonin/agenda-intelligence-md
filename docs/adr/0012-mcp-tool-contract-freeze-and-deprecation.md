# MCP tool contract is frozen at v1.0 with manifest-declared deprecation

Starting with v1.0, all sixteen MCP tools currently exposed by `agenda-intelligence-mcp` — the eleven validation-layer tools (`validate_brief`, `validate_evidence`, `audit_claims`, `verify_quotes`, `score_output`, `get_protocol`, `list_lenses`, `get_lens`, `source_plan`, `source_coverage`, `list_source_categories`) and the five product-layer tools (`analyze`, `validate_memo`, `list_signals`, `get_signal`, `deep_dive`) — are part of the v1.0 compatibility surface defined by ADR 0003. Tool name, presence, `inputSchema` shape, and required-argument set are frozen: a request that is valid against the v1.0 contract MUST remain valid for every subsequent v1.x release. The split into validation layer and product layer is a documentation grouping (see [MCP.md](../../MCP.md)), not a compatibility tier — both layers are equally frozen.

A change to any MCP tool is breaking, and requires a major version bump, when it would make a previously valid v1.x call fail or change semantics. Concretely: renaming a tool, removing a tool without prior deprecation, renaming a field in `inputSchema`, adding a new required argument, narrowing a type (`string` → enum, removing enum values), changing the shape of the returned payload such that existing consumers misread it, or changing the semantic meaning of an existing field. Non-breaking, allowed in minor releases: adding a new tool, adding an optional argument with a safe default, widening a type, adding enum values, adding fields to the returned payload, clarifying a description without changing behavior.

Tool removal goes through a manifest-declared deprecation cycle, not direct removal. The authoritative tool registry lives in `agent-manifest.json` under a new `mcp.tools` array (see ADR 0013), with each entry declaring `name`, `input_schema` (a `$ref` to a schema under `schemas/v1/`), `since` (the version that introduced the tool), and optional `deprecated` and `removal_in` fields. A tool marked `deprecated: true` MUST continue to function for the remainder of the v1.x line; it MAY be removed only in the next major (v2.0). The existing `deep_dive` "Reserved for v2" pattern is the inverse case (planned, not yet active) and stays as-is; it is documented in the manifest with `status: "reserved"` and a stable `inputSchema` so the tool name is not silently repurposed.

The manifest field `mcp_sketch: "MCP.md"` is renamed to `mcp` in v1.0 and changes shape from a pointer to a record: `{ "spec": "MCP.md", "tools": [ … ] }`. `MCP.md` remains as human documentation; the manifest array becomes the machine-readable contract. The `TOOLS` dict in [src/agenda_intelligence/mcp_stdio.py](../../src/agenda_intelligence/mcp_stdio.py) MUST stay in sync with the manifest array; `tests/test_package_consistency.py` is extended (separate implementation PR) to fail if `TOOLS.keys()` and `manifest.mcp.tools[*].name` diverge. Compatibility-surface boundaries inherit from ADR 0003; this ADR fixes their operational shape for the MCP surface specifically.
