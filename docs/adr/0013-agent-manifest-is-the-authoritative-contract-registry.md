# `agent-manifest.json` is the authoritative contract registry, not a pointer file

Starting with v1.0, `agent-manifest.json` carries two kinds of fields with different compatibility semantics. **Contract fields** declare what callers can depend on and are governed by ADR 0003: `name`, `version`, `schemas`, `mcp`, and the as-yet-unfrozen `cli` shape (see follow-ups). A breaking change to any contract field requires a major version bump per ADR 0003. **Informational fields** describe the project for humans and tools but are not part of the compatibility surface: `description`, `repository`, `entrypoint`, `adoption`, `llms`, `analysis_bank`, `protocols`, `lenses`, `source_acquisition`. Informational fields MAY change in any release; consumers MUST NOT rely on their shape for runtime decisions. This split is documented inline in the manifest via a top-level comment block (`_contract_fields` and `_informational_fields` arrays listing field names), so that tooling can verify membership without re-reading this ADR.

The `schemas` map evolves to record both path and major-version explicitly. Each entry becomes an object: `{ "path": "schemas/v1/<name>.schema.json", "schema_version": "v1" }`. Per ADR 0011 the major-version segment lives in the path itself; the parallel `schema_version` field is the machine-readable handle a manifest consumer reads without parsing URLs, and the load-bearing case is a future migration window where one manifest references both v1 and v2 schemas. The `product.request_schema` and `product.response_schema` fields move to the same object form and reference entries in the top-level `schemas` map by key, not by direct path, so the major-version assertion has exactly one source.

The MCP surface lives at top-level key `mcp`, replacing both `mcp_sketch` and `product.mcp_tools`. Shape: `{ "spec": "MCP.md", "tools": [ { "name": "...", "since": "v1.0", "input_schema": { ...inline JSON Schema... }, "deprecated"?: true, "removal_in"?: "v2.0", "status"?: "reserved" } ] }`. Input schemas are inlined in the manifest rather than promoted to files under `schemas/v1/`. The `schemas/` directory is reserved for analytical-artifact contracts (briefs, memos, evidence packs, lens manifests, signal trackers) which are large, cross-referenced, and consumed outside the MCP transport. MCP tool input schemas are small (typically one to three fields), local to the tool, and have no external consumers — promoting each to a file would dilute `schemas/` and create sixteen entries that exist only to satisfy a uniformity rule. The authoritative tool list is `mcp.tools[*].name`; [src/agenda_intelligence/mcp_stdio.py](../../src/agenda_intelligence/mcp_stdio.py)'s `TOOLS` dict mirrors the manifest, and `tests/test_package_consistency.py` is extended in the implementation PR to assert exact equality of names and input-schema content.

Sync invariants the manifest holds, enforced by tests:
- `agent-manifest.json` (top-level) and `src/agenda_intelligence/data/agent-manifest.json` are byte-identical (existing invariant from the dual-copy rule).
- For each entry in `schemas`, the referenced file exists at `path` and its `$id` matches the canonical URL form from ADR 0011.
- `mcp.tools[*].name` and `mcp.tools[*].input_schema` exactly match the `TOOLS` dict in `mcp_stdio.py`.
- For tools with `deprecated: true`, the handler in `mcp_stdio.py` still exists and still routes; for `status: "reserved"`, the handler returns the planned-status payload.
- `version` in the manifest matches the `pyproject.toml` package version.

The `cli` field is intentionally left as the existing string pointer (`scripts/agenda_intelligence.py`) in v1.0 because CLI subcommand contracts have not been triaged for the freeze. This is a known gap. **Follow-up:** ADR 0014 (out of scope for this freeze) decides whether `cli` becomes a structured registry — `{ "command": "agenda-intelligence", "subcommands": [ ... ] }` — analogous to `mcp`. Until then, CLI behavior remains a compatibility surface per ADR 0003 ("CLI behavior"), but the manifest does not enumerate it. Note also that the current `cli` value (`scripts/agenda_intelligence.py`) is informational and likely stale (the real entry point is `python3 -m agenda_intelligence.cli`); correcting that string is part of the implementation PR for ADR 0013, not a contract change.
